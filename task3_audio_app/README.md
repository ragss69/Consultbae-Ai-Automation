# Task 3 — Mini Audio Collection App

A lightweight **Streamlit application for collecting and analyzing audio submissions from ConsultBae gig workers**.

Users can:

* Enter their name and phone number
* Record audio in the browser or upload an audio file
* Submit and store the recording
* Automatically extract audio properties
* View previous submissions
* Play stored recordings

The application uses **Streamlit** for the interface and **SQLite** for submission metadata. Audio files are stored locally.

---

## Architecture

The application uses a single Streamlit process rather than a separate backend and frontend.

```text
User
  ↓
Streamlit UI
  ↓
Validate name, phone & audio
  ↓
Generate unique submission ID
  ↓
Save audio file
  ↓
Normalize phone & match person
  ↓
Extract audio properties
  ↓
Store submission in SQLite
  ↓
Display result
  ↓
View / play previous submissions
```

Streamlit was chosen to keep the application lightweight and easy to demonstrate locally while keeping the processing and database logic separated into reusable modules.

## Audio Processing

For each accepted recording, the application extracts the following properties:

| Property       | Database Field   | Description                                 |
| -------------- | ---------------- | ------------------------------------------- |
| Duration       | `duration_sec`   | Audio length in seconds                     |
| Sample Rate    | `sample_rate_hz` | Audio sampling frequency                    |
| Bitrate        | `bitrate_kbps`   | Encoded or estimated bitrate                |
| Loudness       | `loudness_dbfs`  | RMS loudness relative to digital full scale |
| Noise Estimate | `noise_estimate` | Optional heuristic quality indicator        |

### Loudness

Loudness is represented using **RMS amplitude in dBFS** and stored as `loudness_dbfs`.

It is intentionally not described as LUFS because the application does not implement a LUFS measurement.

### Bitrate

Depending on the audio format, bitrate may be read directly from the file or estimated from the available audio metadata.

## File Validation

Before processing an audio submission, the application validates:

* Name is not blank
* Phone has a minimally valid structure
* Audio file is present
* File is not empty
* File size is within the configured limit
* File extension/MIME type is supported
* Audio can be successfully decoded

The application does not rely solely on the browser-provided MIME type; the file is also validated during decoding.

---

## Safe File Storage

User-provided filenames are **never used directly as filesystem paths**.

Instead, the application generates a unique stored filename using the submission ID or UUID while preserving the original filename separately in the database.

This prevents:

* Filename collisions
* Accidental overwrites
* Path traversal
* Invalid filesystem paths

Audio files are stored under:

```text
audio_files/
```

This directory is generated locally and excluded from Git.

## Person Matching

The application attempts to associate each submission with a Task 1 person using the submitted phone number.

Phone numbers are normalized before matching so that different representations of the same number can be compared consistently.

### Matching Rules

| Condition                                  | Result                                    |
| ------------------------------------------ | ----------------------------------------- |
| Unique phone match + compatible name       | Link to `person_id`                       |
| Unique phone match + serious name conflict | Retain submission and flag conflict       |
| Phone not found                            | Retain submission with `person_id = NULL` |
| Phone linked to multiple people            | Mark match as ambiguous                   |
| No safe match                              | Do not force an association               |

A submission is **not rejected solely because the person cannot be matched** to Task 1.

The original submitted name and phone number are retained even when a `person_id` is found.

## Database

Task 3 uses the Task 1 SQLite database and adds an `audio_submissions` table.

The relationship is:

```text
persons
   │
   └── audio_submissions
```

A single person can have multiple audio submissions.

### `audio_submissions`

Key fields include:

```text
submission_id
person_id
submitted_name
submitted_phone
normalized_phone
match_status
match_method
original_filename
stored_filename
mime_type
file_size_bytes
file_path
duration_sec
sample_rate_hz
bitrate_kbps
bitrate_method
loudness_dbfs
noise_estimate
processing_status
processing_error
submitted_at
```

### Schema Decisions

#### Nullable `person_id`

A submission may come from someone who cannot be safely matched to Task 1, so `person_id` is nullable.

#### Raw and Normalized Values

Both versions of user-provided values are retained:

* Raw values preserve the original submission.
* Normalized values support matching and querying.

#### Separate Submission ID

`submission_id` uniquely identifies an audio submission and is separate from `person_id`.

This allows one person to submit multiple recordings.

#### Processing Status

Processing status records whether the submission completed successfully.

Typical statuses include:

```text
processing
completed
failed
rejected
```

If audio analysis fails, the error is recorded rather than silently discarding the submission.

## Submission Flow

```text
Enter name and phone
        ↓
Record or upload audio
        ↓
Validate form and file
        ↓
Create submission ID
        ↓
Save audio using generated filename
        ↓
Normalize phone
        ↓
Attempt person matching
        ↓
Create submission record
        ↓
Extract audio properties
        ↓
Update processing status
        ↓
Display result
```

If audio analysis fails:

* The error is recorded.
* The submission is marked as failed.
* The application does not present it as successfully processed.
* File cleanup follows the application's configured policy.

## Error Handling

The application handles or reports:

* Missing name
* Invalid phone input
* Missing audio
* Empty audio file
* Unsupported format
* Oversized file
* Corrupted audio
* Audio-analysis failures
* Missing Task 1 database
* Missing `persons` table
* Missing stored audio file
* Ambiguous or conflicting person matches

Errors are surfaced to the user and recorded where appropriate.

## Known Limitations

* Designed as a local prototype rather than a high-concurrency production system.
* Audio files are stored on the local filesystem.
* SQLite is not intended for high-concurrency production traffic.
* Person matching is intentionally conservative and may leave some submissions unmatched.
* Browser recording behavior depends on browser and Streamlit support.
* Bitrate may be estimated for formats without directly available bitrate metadata.
* Loudness uses RMS dBFS and should not be interpreted as a universal studio loudness standard.
* The optional noise estimate is heuristic rather than a validated audio-quality model.
* There is no authentication or user account system.
* Duplicate recordings are retained as separate submissions.
