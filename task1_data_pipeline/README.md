# Task 1 — Data Merge Pipeline

Merges three inconsistent CSV exports (Naukri applicants, Gig Workers, CBNexus contacts) into one SQLite database, resolving the same person appearing across files into a single canonical record — without any shared ID field across the sources.

## Setup

```bash
cd task1_data_pipeline
pip install -r requirements.txt
python src/pipeline.py
```

Reads from `data/raw/`, produces `data/processed/consultbae.db`. The database is a build artifact — it's gitignored and regenerated by running the command above.


## Approach

1. **Structural triage** — blank rows, the repeated CBNexus header, and a shifted Gig Worker row are quarantined before any matching logic runs.
2. **Normalization** — emails, phones, cities, and dates are normalized for comparison; raw values are always preserved.
3. **Within-source grouping** — rows sharing an identifier (email/phone) are grouped, but only merged if they don't internally conflict on other identifiers.
4. **Cross-source linking** — Source 1 (Naukri) is used as the bridge, since it's the only file with both email and phone. Source 2/3 records link only on an exact, exclusive, uncontradicted match.
5. **Everything else** — no safe match becomes a new person or is flagged ambiguous. Name+city alone is never sufficient to merge — only to generate review candidates.


## Schema

```
persons             — one row per resolved person
source_records      — one row per original CSV row (all 3 sources), raw + normalized fields, linked to a person_id once resolved
quarantine_records  — structurally broken rows, never entity-resolved
match_log           — every match decision made, with method, outcome, and evidence
```

A single unified `source_records` table is used instead of three source-specific tables, to cut schema boilerplate and stay easy to extend.

## Data issues found and how they were handled

| Issue | Where | Handling |
|---|---|---|
| Inconsistent email casing | Naukri | Normalized to lowercase before comparison |
| Inconsistent phone formats (`+91-...`, `0...`, bare 10-digit) | All 3 files | Normalized to one canonical 10-digit form |
| City name variants (Bangalore/Bengaluru, Gurgaon/Gurugram, Delhi/New Delhi/Delhi NCR) | All 3 files | Profiled actual distinct values, then built a small documented alias map |
| Mixed CTC/rate units | Naukri, Gig Worker | Normalized to consistent numeric fields, raw value preserved |
| Inconsistent/ambiguous date formats | Naukri | Parsed deterministically where possible; genuinely ambiguous cases default to DD-MM-YYYY, flagged (`date_parse_status = ambiguous_default`) |
| Blank row | Gig Worker file | Quarantined, excluded from matching |
| Repeated header row mid-file | CBNexus file | Detected and excluded |
| Shifted/malformed row (values offset by one column) | Gig Worker file | Quarantined rather than auto-repaired — a clean version of the same person already existed elsewhere in the file |
| Same person, same strong identifier, minor variation elsewhere (e.g. two emails for one phone) | Naukri | Treated as a duplicate/formatting variant, merged, both variants retained |
| Same name + city, no corroborating identifier ("Arjun Mehta" appearing 3 times with mismatched phones/emails) | Naukri, CBNexus, Gig Worker | Only the record with a matching identifier was merged; the others left unresolved rather than merged on name+city alone |
| Same identifier shared across records with conflicting other identifiers | Cross-source | Detected before merging; conflicting rows quarantined for review |

## Known limitations

- Ambiguous/quarantined records are surfaced for review, not resolved automatically — by design.
- The city alias map covers only variants observed in this dataset, not a general gazetteer.
- Ambiguous dates default to DD-MM-YYYY (India-context assumption) rather than being guessed silently.

# Task 1 — ConsultBae Data Merge Pipeline

This project ingests three inconsistent CSV exports used by ConsultBae and consolidates them into a single SQLite database.

The source systems do not share a common ID field, so the pipeline uses normalized email and phone values to resolve records belonging to the same person. Ambiguous records are not force-merged; they are preserved and surfaced for review.

The pipeline is designed around four principles:

1. Preserve the original source data.
2. Normalize values before comparison.
3. Auto-merge only when the identity evidence is strong and unambiguous.
4. Make every important decision explainable and auditable.

## Problem Context

The assignment provides three independent data exports:

- **Naukri applicants** — includes name, email, phone, city, experience, CTC, application date, and skills.
- **Gig workers** — includes name, email, rate, location, status, and skills.
- **CBNexus contacts** — includes name, phone, city, verification status, and completed projects.

No single identifier exists across all three datasets:

- Naukri contains both email and phone.
- Gig Workers primarily provides email.
- CBNexus primarily provides phone.

Therefore, the Naukri dataset acts as the initial bridge between the other two sources:

```text
Gig Workers ── email ──> Naukri <── phone ── CBNexus
```

This bridge is useful, but it is not treated as a requirement. Records without a safe Naukri match may still become new person records or remain unresolved for review.

## Setup

### Requirements

- Python 3.10 or later
- pip
- SQLite, included with most Python installations

### Install dependencies

From the Task 1 directory:

```bash
cd task1_data_pipeline
pip install -r requirements.txt
```

### Add the input files

Place the three original CSV files in:

```text
data/raw/
```

The pipeline expects the source files to be available in that directory. If the filenames are configured in `src/pipeline.py`, they should match the expected names used by the pipeline.

### Run the pipeline

```bash
python src/pipeline.py
```

The pipeline will:

1. Read all three CSV files.
2. Perform structural validation.
3. Quarantine invalid rows.
4. Normalize comparison fields.
5. Deduplicate records within each source.
6. Resolve high-confidence cross-source matches.
7. Create canonical person records.
8. Record matching decisions and evidence.
9. Write the final SQLite database.

The generated database is written to:

```text
data/processed/consultbae.db
```

The database is a generated build artifact and is intentionally excluded from Git. It can be recreated at any time by running the pipeline again.

## Database Schema

The pipeline creates four main tables.

### `persons`

Contains one row per resolved person.

This is the canonical entity table. It does not replace the original source records; it provides a stable `person_id` that can be referenced by other tables and future tasks.

Typical information includes:

- `person_id`
- canonical or preferred name
- canonical email, where available
- canonical phone, where available
- canonical city, where available

### `source_records`

Contains one row for each accepted original CSV record.

This table preserves:

- source name;
- original source row number;
- raw source values;
- normalized comparison values;
- the resolved `person_id`, when a safe match exists.

Keeping source records separate from canonical persons prevents information loss and makes every merge traceable.

### `quarantine_records`

Contains rows that should not enter entity resolution because they are structurally invalid or unsafe to process.

Examples include:

- blank rows;
- repeated header rows;
- shifted-column rows;
- malformed records;
- records that require a human decision before processing.

Each quarantined row retains its source and reason.

### `match_log`

Contains the decisions made by the matching pipeline.

It records information such as:

- source record;
- candidate person;
- matching method;
- outcome;
- confidence category;
- evidence;
- conflict or review reason.

Typical outcomes include:

- `matched`;
- `duplicate_variant`;
- `new_person`;
- `ambiguous`;
- `conflict`;
- `quarantined`.

## Entity Resolution Strategy

### Strong identifiers

The primary matching fields are:

- normalized email;
- normalized phone.

A record is automatically linked only when the identifier is:

1. normalized successfully;
2. unique;
3. associated with exactly one existing person;
4. not contradicted by another strong identifier or serious identity evidence.

An exact identifier is treated as strong evidence, but not as unconditionally safe. The pipeline detects identifier collisions and contradictory records before merging.

### Cross-source matching

The current strategy is:

| Source | Primary matching field |
|---|---|
| Gig Workers | Normalized email |
| CBNexus | Normalized phone |
| Naukri | Email and phone used to create the initial identity anchors |

Name and city are not used as automatic merge triggers.

### Name and city

Name and city are used only to generate review candidates.

They are not sufficient for automatic merging because multiple people can have:

- the same name;
- the same city;
- similar names with different contact details.

For example, the data contains multiple `Arjun Mehta` records. Only the record supported by a matching normalized phone is automatically linked. Other Arjun Mehta records remain separate or unresolved unless stronger evidence becomes available.

### Conflict handling

The pipeline does not blindly merge records into one connected component when identifier chains conflict.

For example:

```text
Record A: email X, phone 1
Record B: email X, phone 2
Record C: email Y, phone 2
```

A naïve graph-based approach could merge all three records. This pipeline instead detects the conflict and sends the affected records for review.

## Normalization Rules

Raw values are always preserved. Normalized values are stored separately for comparison and querying.

### Email

- Trim leading and trailing whitespace.
- Convert to lowercase.
- Do not apply aggressive transformations such as removing dots or plus-addressing.

Example:

```text
ISHA.CHOPRA95@MAILTEST.EXAMPLE.ORG
```

becomes:

```text
isha.chopra95@mailtest.example.org
```

### Phone

Phone numbers are normalized to a common Indian 10-digit representation where possible.

Formatting differences handled include:

```text
+919000000211
+91-9000000211
919000000211
09000000211
9000000211
```

The original phone value remains available in the source record.

### Name

Names are normalized for comparison by:

- trimming whitespace;
- converting to lowercase;
- collapsing repeated whitespace;
- normalizing punctuation where appropriate.

Name normalization is supporting evidence only and does not independently prove identity.

### City

The distinct city values were profiled before creating a small explicit alias map.

Examples include:

```text
Gurgaon   → Gurugram
Bangalore → Bengaluru
```

Delhi-related values such as `Delhi`, `New Delhi`, and `Delhi NCR` are handled according to the documented comparison rule. They are not assumed to represent exactly the same canonical location in every context.

### Dates

Dates are parsed into a consistent format where possible.

The original date string is retained.

Parsing behavior:

- ISO dates are parsed directly.
- Text dates such as `7 Jul 2026` are parsed directly.
- Dates with an obviously invalid month/day combination are interpreted using the only valid format.
- Genuinely ambiguous dates use the documented DD-MM-YYYY default because the data is India-context.
- Ambiguous defaults are flagged with:

```text
date_parse_status = ambiguous_default
```

Dates are not used as primary entity-matching identifiers.

### Compensation and rates

The source files contain semantically different values, including:

- annual CTC;
- CTC represented in lakhs;
- hourly rates;
- monthly rates.

Raw compensation values are retained. Normalized values include unit information rather than forcing all values into one misleading numeric field.

Examples:

```text
1415/hr
15k/month
417964
5.1
```

These values should not be treated as directly comparable unless their unit and period are known.

## Data Quality Issues Found

| Issue | Source | Handling |
|---|---|---|
| Inconsistent email casing | Naukri and Gig Workers | Lowercased and trimmed before comparison; raw values preserved |
| Inconsistent phone formatting | All sources | Converted to a comparable normalized phone representation |
| Leading zeroes and country-code variants | All sources | Normalized before matching |
| City casing and whitespace differences | All sources | Trimmed and normalized |
| Gurgaon/Gurugram variation | Naukri, Gig Workers, CBNexus | Explicit alias mapping |
| Bangalore/Bengaluru variation | Multiple sources | Explicit alias mapping |
| Delhi/New Delhi/Delhi NCR variation | Multiple sources | Handled using documented comparison rules |
| Mixed status casing | Gig Workers | Normalized to controlled comparison values |
| Mixed verification values | CBNexus | Normalized while preserving raw values |
| Mixed skill casing | Gig Workers and Naukri | Normalized for comparison and categorization |
| Mixed CTC and rate units | Naukri and Gig Workers | Raw value preserved; unit and period retained separately |
| Ambiguous date formats | Naukri | Parsed using documented rules and flagged where a default was required |
| Blank row | Gig Workers | Quarantined and excluded from matching |
| Repeated header row | CBNexus | Detected, quarantined, and excluded |
| Shifted/malformed row | Gig Workers | Quarantined rather than repaired by guessing |
| Same person with name variation | Naukri | Linked when supported by the same strong email/phone identifier |
| Duplicate or variant records | Naukri | Grouped only when strong identifiers agree and no conflict exists |
| Same name and city with different identifiers | Multiple sources | Not automatically merged |
| Multiple Arjun Mehta records | Naukri, Gig Workers, CBNexus | Only the identifier-supported match was merged; remaining records were kept separate or flagged |
| Conflicting strong identifiers | Cross-source | Detected and sent for review rather than force-merged |

The database should contain:

- one canonical `persons` record for each confidently resolved person;
- source-level records linked to `person_id` where a safe match exists;
- unmatched records represented as new people or unresolved records;

## Inspecting the Database

If the SQLite command-line tool is available:

```bash
sqlite3 data/processed/consultbae.db
```

Then inspect the tables:

```sql
.tables
```

Check the number of canonical people:

```sql
SELECT COUNT(*) FROM persons;
```

Check source records:

```sql
SELECT source_name, COUNT(*)
FROM source_records
GROUP BY source_name;
```

Check match decisions:

```sql
SELECT outcome, COUNT(*)
FROM match_log
GROUP BY outcome;
```

Check unresolved or ambiguous records:

```sql
SELECT *
FROM match_log
WHERE outcome IN ('ambiguous', 'conflict');
```

Exit SQLite with:

```text
.quit
```

If the pipeline provides a validation or reporting command, that command should be preferred because it presents the results in a more readable format.

## Why a Unified `source_records` Table Was Used

A unified source-record table was chosen instead of three separate source-specific tables.

This keeps the schema smaller and avoids duplicating the same provenance and matching columns across three tables.

The table can distinguish source-specific records using a `source_name` field while retaining:

- the original source row;
- raw values;
- normalized values;
- source-specific attributes;
- the associated canonical `person_id`.

This structure is also easier to extend if ConsultBae adds another source later.

---

## Why Ambiguous Records Are Not Force-Merged

The objective is not to maximize the number of merged rows at any cost.

A false merge is more damaging than an unresolved record because it corrupts the canonical person record and can incorrectly combine:

- contact information;
- compensation;
- experience;
- skills;
- project history.

The pipeline therefore prefers:

```text
safe match > explicit ambiguity > incorrect merge
```

This is particularly important for the repeated `Arjun Mehta` records, where name and city are not enough to determine identity.

---

## Known Limitations

- The alias map covers variants observed in the supplied datasets and is not a general geographic gazetteer.
- The pipeline does not claim that every record can be resolved automatically.
- Ambiguous records require human review.
- Dates with insufficient information use a documented India-context default.
- Compensation normalization is unit-aware but does not make hourly, monthly, and annual values directly comparable without additional business assumptions.
- The pipeline does not use fuzzy matching for automatic merging.
- Fuzzy or name/city candidates are used only to support review.
- The SQLite database is generated locally and is not committed to Git.
- The source data is synthetic/assignment data and should not be treated as production data.
